# IM 测试缺口反思：为什么“添加好友”断链无人发现（2026-09-04）

## 事故定性

用户开箱即卡死：聊天页零好友，空态提示“添加好友后即可开始私聊”，
但全界面没有任何添加好友入口。后端命令、IPC 契约、mock 三层全部就绪
（chatFriendAdd / chatFriendRemove 自 T30/T32 起可用），唯 GUI 零调用点。
能力在，入口无。T34-T36 三轮边界测试期间无一人发现。

## 反思：四个根因

1. **测试从实现出发，不从用户旅程出发。**
   既有 GUI 测试全部用 fixtures 预置好友列表后测渲染/发送/分页——
   好友从天而降，没有任何测试问过“第一个好友从哪来”。
   单元/集成/边界三层齐备，却漏掉最朴素的从零开始路径。

2. **断言了 UI 的承诺，没验证承诺可兑现。**
   chat-view.test 断言空态渲染引导文案“添加好友后即可开始私聊”，
   而界面根本没有添加入口。测试成了文案断言器，不是行为验证器。

3. **没有“契约能力-界面入口”对账机制。**
   契约每加一个命令，前端应有对应 UI 调用点或显式“暂不暴露”决策。
   chatFriendAdd/chatFriendRemove 在 views/components 下零调用点，
   一条静态扫描（grep 调用点 + 豁免清单）即可机械拦下，从未建立。

4. **边界轮在已建成模块上堆料，方向性偏差。**
   T34-T36 给 composer/store/model 补了 24+ 边界用例（空文本、2000 字符、
   64MiB、乱序事件……），越测越细、越测越深，却越测越偏离
   “用户能否走通第一步”。细度不等于覆盖，深度不等于正确方向。

## 整改（本轮落地）

- IM-T41：添加好友入口 + 表单 + 从零开始旅程测试（空态→添加→出现→选中→发消息）
- IM-T42：移除好友入口 + 确认框 + 添加/移除/回加旅程测试
- 两条机械守卫入测试套：
  a. 入口存在性断言（空态与常态均可达添加入口）；
  b. IpcBackend 全部 chat 方法在 GUI 源码至少一个调用点（豁免清单制）。
- IM-T43（待派）：好友分组——需契约加法修订（ChatFriendJson 增分组字段），
  先登记，等 T41/T42 合入后由协调会话裁决派单。

## 红线沉淀（进 skill / 账本纪律）

- 每个面向用户的功能页验收必须含一条“从零开始”旅程测试；
  fixtures 预置数据前，先测数据从哪来。
- 空态文案是承诺；凡写了“XX后即可YY”的引导，必须有通往 XX 的入口，
  且测试必须从空态点击走到 YY。
- 新增 IPC 契约命令时，同轮提交调用点清单（UI 调用 / 显式豁免二选一），
  守卫测试机械兜底。
