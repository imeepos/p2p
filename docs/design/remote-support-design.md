## 1. 商业场景与产品定义

用户电脑出问题自己解决不了，付费找人处理。存量供给是人工远程支持
（向日葵/TeamViewer + 人工坐席，单均 ¥50-200，付费意愿已被市场验证）。
本产品把"那个人"换成 AI：**服务商侧的 AI agent 在用户授权且付费的前提下，
经临时 MCP server 远程操作客户机的文件系统与命令行**，完成诊断、修复与交付。

本轮已拍板的商业参数：

| 参数 | 拍板 | 理由 |
|---|---|---|
| 平台 | Windows 10/11 优先 | 付费求助人群最集中；UAC 弹窗天然是一层确认机制 |
| AI 自主度 | v1 playbook 化 | 每类问题预定义诊断/修复/验证步骤集，agent 只做步骤内自适应 |
| 收费 | 免费只读诊断 + 按单付费 | 免费体检是获客钩子兼预分类定价依据；会员制后置 |
| 兜底 | 复杂单转人工坐席 | 目标 AI 闭环 60%+；人工单定价更高 |
| **大脑** | **任意 agent 接入：DSH / Codex / Claude Code 等** | **agent 是供给不是产品；模型进化随时换脑不换道** |

接入机制拍板：**客户机端点提供临时 MCP server**。MCP 是主流 agent 的共同工具协议
（Claude Code、Codex、Cursor、DSH 均原生支持 MCP client），以它为执行面，
服务侧大脑完全可替换、可竞争、可路由。

v1 问题目录（8 类，playbook 逐个人工打磨）：
电脑卡慢 / 弹窗流氓软件清理 / C 盘空间不足 / 网络掉线诊断 / 软件装卸修复 /
打印机驱动 / 蓝屏日志初筛 / 浏览器劫持。

## 2. 第一公理与拓扑裁决

**第一公理（不变）：客户机端点不含任何 AI 能力（无模型、无 prompt、无 playbook）。**
agent 若落在客户机，客户装上它就不再需要本服务——产品亲手交付了核心价值。
因此唯一可行拓扑是 C：**大脑在服务商侧，客户机是受控的哑执行端点**。

v1 修订的是 C 的实现形态：

- v0 设想：自研 /rsh/1 协议 + harness 侧 fs-p2p/bash-p2p 后端（绑定 DSH）；
- **v1 拍板：临时 MCP server 承载全部工具语义 + 标准 MCP 接入桥；自研协议取消，
  工具面即产品 API。**

为什么 MCP 赢：

1. **生态零成本**：服务侧任何 agent 天生会说 MCP，无需为每个 agent 写执行后端
   （对比 v0 的 fs-p2p 只服务 DSH 一家）；
2. **结构化即安全**：MCP tool 自带参数 schema，风险分级与执法粒度天然细到参数级；
3. **竞争中立**：大脑层按问题类型路由最优 agent、失败换脑重试；护城河收敛到
   工具面设计、playbook、平台闭环与信任——这些本来才该是产品。

保留的 v0 结构性收益，在 MCP 工具面下表达更自然：

- **信任倒置**：执法点在客户机本地，"agent 能做什么"由助手名单引擎独立裁决，
  服务商标签只是建议。"谁的主机谁做主"是营销主打点；
- **支付=scope 升级**：diag scope 只读 tools 可用；fix scope 写类 tools 需逐条托盘批准。

## 3. 总架构

```
服务商侧（大脑可插拔）                          客户机（薄，Rust，无任何 AI）
┌────────────────────────────────┐            ┌────────────────────────────────┐
│ 工单调度（接单/路由/发 token）    │            │ 「维修助手」                     │
│ Agent Runner 池：               │            │  = 临时 MCP server（工单期存活）  │
│  DSH / Codex / Claude Code      │  p2p 隧道   │  ├─ tools：fs/shell/诊断/备份    │
│  （统一 runner 抽象）            │◄══════════►│  ├─ 本地执法引擎（权威）          │
│ 接入桥 repair-bridge             │  stdio⇄流  │  ├─ 托盘：授权/审批/反馈/急停     │
│ （stdio ⇄ p2p 双向泵）           │            │  └─ 审计+备份+修改记录            │
│ playbook 库（agent 无关）        │            │  收货即停——临时性是安全属性        │
│ 工单页：交付/验收/反馈/收货/评价  │            └────────────────────────────────┘
└────────────────────────────────┘
```

| 组件 | 形态 | 职责 |
|---|---|---|
| 维修助手 | Windows 安装包（Rust bin） | 临时 MCP server 宿主 + 本地执法 + 托盘 UI + 审计备份；不含任何 AI |
| 接入桥 repair-bridge | 服务侧小进程 | stdio 上的 MCP JSON-RPC ⇄ p2p 流双向哑泵，每工单会话一个 |
| Agent Runner 池 | 服务侧 | 统一抽象下驱动 DSH / Codex / Claude Code 各 runner 执行工单 |
| playbook 库 | agent 无关格式 | 8 类问题 ×（诊断/修复/验证）步骤集 + 红线清单 |
| 工单/支付/交付页 | Web | 0-6 闭环：下单→接单→授权→执行→交付反馈→收货→评价 |

## 4. 工单生命周期（0-6 全闭环）

```
0 客户下单（描述问题，可选先跑免费只读体检）
1 服务端接单（按问题类型路由 agent runner，生成 ticket token）
2 客户端授权（助手拉起临时 MCP server；托盘授权 scope+时效；出站注册到调度）
3 执行（runner 经桥驱动工具面；敏感调用托盘逐条批准；全程留痕）
4 交付与验收（执行记录+文件修改记录上工单页；不满意→实时反馈→修复轮回 3，
  可多轮；反馈期间 token 续期）
5 确认收货（token 焚毁、MCP server 停止、还原点进入保留期）
6 提交评价（关单归档、评价入信誉体系）
```

反馈闭环要点：

- **执行完成不等于关单**：第 4 步是带多轮反馈的验收区，交付物（§7）是验收依据；
- 反馈通道：工单页文字/截图；助手可按需跑验证 playbook 自动复核客户描述；
- token 生命周期：授权时生效，**确认收货即焚**（不按修复完成焚）；硬上限累计 24h（Q2）。

## 5. 工具面：临时 MCP server 暴露什么

临时性：MCP server 内嵌于维修助手进程，接单+授权时拉起，收货/超时即停；
ticket token 一次性、绑定工单与对端 PeerId、带时效。

| tool | 语义 | 风险档 |
|---|---|---|
| sys_snapshot | 系统信息快照（体检与诊断第一入口） | read |
| fs_read / fs_list / fs_search | 只读文件访问（授权根监狱内） | read |
| fs_write / fs_edit | 写改文件：内部先备份原件、产出 diff 记录、返回修改凭据 | write |
| shell_exec | argv 数组 + cwd（监狱）+ timeout + reason；输出截断 | 本地按命令重判（write/danger） |
| backup_point | 系统还原点 / 目录快照 | write |
| proc_query / svc_query / net_diag | 进程/服务/网络诊断（只读） | read |
| session_report | 导出本工单执行记录与修改清单（交付物数据源） | read |

审批语义：write/danger 调用在助手内部挂起 → 托盘弹窗（tool、参数摘要、reason、
diff）→ 批准则执行；**60s 超时 = 拒绝**（无人值守即拒绝，沿 acp 红线）；
agent 侧表现为该次调用延迟或收到带原因的拒绝错误，对任何 agent 行为一致。

拍板项：

1. **双面分离**：能用 fs_* 结构化工具完成的一律不走 shell_exec；
2. **路径监狱**：全部 fs 工具的路径参数强制解析在授权根内，越界即拒；
3. **输出门禁**：单结果大小上限 + 截断标志，杜绝内存炸弹；
4. **断线语义**（沿 acp §5）：执行中调用由助手续跑完并缓存结果，桥重连后补投；
   挂起中的审批遇断线 = 拒绝。

## 6. 传输与接入桥

- 客户机：助手出站连接调度（底座直连→打洞→中继降级链），按 ticket 注册；
- 服务侧：agent 的 MCP 配置指向本地 stdio 命令 repair-bridge --ticket TOKEN；
  桥出站找到对端后，把 stdio 上的 MCP JSON-RPC 与 p2p 流双向对拷；
- **三行配置即接入**：任意 agent 执行 mcp add 挂上桥即可用，桥不解析 MCP 语义
  （版本协商在 JSON-RPC 层透传），协议升级不碰 Rust；
- 隧道流协议 ID 按底座语法登记；帧与分块复用底座既有设施。

## 7. 交付物：执行记录与文件修改记录

第 4 步验收的实体就是这两份记录（助手与平台双写，责任认定零争议）：

- **执行记录**：时间线视图——每条工具调用含 agent 标识、playbook 步骤号、
  tool+参数摘要、风险档、是否经人工批准、结果与耗时；
- **文件修改记录**：每次修改 = 路径 + 前后 diff + 备份位置 + 关联步骤；
  收货页直接渲染 diff，客户逐条过目；
- **回滚**：文件级按修改记录逆序一键恢复；系统级靠还原点；
- **收货门槛**：确认收货按钮仅在交付物已生成且无未关闭反馈轮时可点。

## 8. 安全模型：双端执法

| 层 | 机制 | 执法点 |
|---|---|---|
| L1 授权 | 托盘授权：scope(diag/fix) + 时效，用户主动发起 | 客户机 |
| L2 分级 | 每次工具调用按 tool schema + 参数预分类 read/write/danger | 双端（发送侧打标，接收侧独立重判） |
| L3 确认 | 敏感调用逐条托盘审批（写文件/删改/注册表/网络配置/凭据相关） | 客户机（权威） |
| L4 兜底 | 写前自动备份+还原点；文件级逆序回滚 | 客户机 + playbook 步骤强制 |
| L5 观测 | 托盘实时调用横幅 + 双向全量审计留存 + 急停 | 双端 |
| L6 合同 | 电子授权书、赔付上限、责任保险 | 平台层 |

红线（客户机无条件拒绝，不提供任何开关）：format/低级磁盘操作、触碰密码凭据、
加密用户文件、批量删除、使杀毒软件失效。

**多 agent 时代的新防线——提示注入**：客户机文件内容会进入 agent 上下文，
恶意构造的内容可能诱导 agent 越权调用工具。对策三层：工具结果以不可信文本标注、
playbook 红线约束、客户机执法兜底——**无论 agent 被怎么骗，写类调用仍需托盘批准**。
注入的最后防线在客户机，这是双端执法在多 agent 架构下的新价值。

## 9. 服务侧平台件

- **Agent Runner 抽象**：统一输入（工单上下文/playbook/桥接入参数）、统一输出
  （结构化执行日志+报告）；适配器很薄，因为 MCP 是共同语言：DSH 会话挂 mcpServers、
  Codex 走 exec/proto、Claude Code 走 headless stream-json；
- **路由**：playbook 声明推荐 runner；失败自动换 runner 重试；解决率/耗时/成本
  数据反哺路由策略；
- **playbook 改为 agent 无关格式**：结构化 markdown（前置条件/步骤/验收命令/红线），
  v0 对 DSH skills 的专有绑定取消；
- LLM key：各 runner 自管，永不落客户机；
- 工单页六段式：下单 / 授权状态 / 执行中（操作流只读视图）/ 交付验收（含反馈入口）
  / 收货 / 评价。

## 10. MVP 裁剪与分期

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0a（零代码，可立即并行） | 手动服务 10 个真实单（人当执行器），验证付费意愿与解决率 | 付费转化与解决率数据 |
| P0b（最小产品） | 助手最小版（sys_snapshot + fs 只读 + shell 白名单闭集）+ 桥 + 单 runner + 执行记录交付 | 真机完成 3 类问题诊断+修复各 1 例 |
| P1 | fs_write+diff 备份回滚、多 runner 路由、支付、反馈闭环工单化、8 类 playbook、收货评价 | 商业闭环：0-6 全流程走通 |
| P2 | 会员制、runner 竞价与 AB、screen 工具（经确认）、评价驱动信誉分 | — |

前置依赖：底座 M1/S/M3 已合入、ECS bootstrap 在线，隧道无阻塞；若个别环节延期，
桥可先退化为中继直连模式，对 agent 侧接口不变。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|---|
| AI 误操作损坏用户数据 | 双端执法 + 逐条审批 + 自动备份/还原点 + 责任保险 |
| 提示注入诱导 agent 越权 | 不可信文本标注 + playbook 红线 + 客户机执法兜底（§8） |
| 合规（PIPL 个人信息） | 默认不读取个人文件；诊断数据脱敏；留存边界见 Q8 |
| 通道被滥用变后门 | token 一次性+绑 PeerId+时效+收货即焚；MCP server 非工单期不存在 |
| runner 输出质量方差 | playbook 约束 + 换脑重试 + 路由数据驱动 |
| MCP 生态演进 | 桥不解析语义、版本协商透传；pin 协议版本随 agent 侧升级 |
| 未签名安装包被 SmartScreen 拦 | 代码签名证书硬成本 |
| 低配客户机资源 | 助手常驻内存目标 < 50 MB；大输出截断 |

## 12. 明确不做（负空间即设计）

- 客户机不放任何 AI 组件（第一公理，无例外）；
- 不自研工具协议（MCP 已够用，v0 的 /rsh/1 取消）；
- 不绑死单一 agent（runner 可插拔是架构属性，不是可选项）；
- v1 不做自由 agent（无 playbook 护栏的裸会话）、不做无人值守修复；
- macOS / 移动端不进 v1；
- 不做 durable 权限、不凭据上 wire、不自定义加密（全用底座既有安全层）。
