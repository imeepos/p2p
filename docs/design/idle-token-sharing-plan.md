# 闲置 LLM 额度共享网络方案(barter-first)

> 状态:草案 v0(待审核) | 日期:2026-09-04
> 依赖:[p2p-base-design.md](p2p-base-design.md)(底座分层)、[wire-protocol.md](wire-protocol.md)(协议 ID 与帧)、
> [../research/p2p-legal-risk-cn.md](../research/p2p-legal-risk-cn.md)(合规红线,本文 §8 全文对齐其结论)
> 定位:底座之上的应用层方案。不改通信内核,只新增应用协议与 crate。

## 1. 背景与动机

节点持有 LLM 上游额度(订阅套餐/充值包,带有效期),普遍存在闲量:月底用不完即清零。
本方案让闲量在互相认识的节点间流转:我闲你用、你闲我用,以 usage 互换记账(barter)结算净差。

核心判断(讨论结论,方案据此定型):

1. **标的物三特殊性**:严格易逝(到期清零,出借动机天然强)、边际成本为零(定价的本质是风险补偿而非租金)、
   借的是与上游合同的履行能力(上游 ToS 风险自始存在,只能管理不能消除)。
2. **先 barter 后 currency**:记账互换不需要充值、定价、法币通道,博弈最简、合规风险最低。
   货币化是 barter 摩擦(单向逆差、无法结算净差)大到不可忍时的演进结果,由需求拉动,不预置。
3. **信任先于规模**:早期网络就是信任网络(PeerId 白名单),治理机制的价值在于让出借方的下行风险可控,
   网络才转得起来。

## 2. 目标与非目标

### 2.1 目标(Phase 0 交付)

- G1 OpenAI 协议兼容:客户端以标准 `/v1/chat/completions`(含 stream)接入,零改造。
- G2 双边 barter 记账:按模型记录上游 usage(输入/输出 token 分列),append-only 流水,账期净差可见。
- G3 预授权-结算两阶段:调用前冻结估算额度,完成后按实际 usage 结算,签名收据为凭。
- G4 白名单准入:出借方按 PeerId allowlist 控制谁能用;双向声明(愿借/愿出)。
- G5 争议与责任:收据验签、争议窗口、封号责任分摊规则、黑名单。
- G6 服务发现:能力声明(模型/余量/账期/TTL)进 rendezvous 注册记录。

### 2.2 非目标(显式排除)

- N1 充值/变现/交易:不接法币通道,不做可提现、可转让余额(合规红线,见 §8)。
- N2 开放撮合/匿名准入:无全局市场,陌生人默认不可见不可用。
- N3 内容代理优化:不做翻墙、不做国际信道规避(legal §3.7 刑事红线)。
- N4 多上游聚合路由的智能选路:Phase 0 只做"买方选定卖方"的直连交易。

## 3. 核心模型

### 3.1 双层额度观

```
锚定层(储备): 上游 API 真实额度,按模型计,带有效期(易逝)
流通层(账本): 节点间 usage 流水与净差,记账单位 = 上游 token(按模型),不设独立积分
```

barter 阶段流通层不引入独立货币单位。每次代理调用是一笔双边流水:
借方(使用方)记负、贷方(出借方)记正,记账凭据为上游返回的 usage + 出借方签名收据。

### 3.2 账期与易逝性

- 流水带账期(默认自然月,可与套餐周期对齐)。账期内净差 = 我用别人的 − 别人用我的。
- 净差不是债务凭证,不跨期累积生息;清账方式:下期多出借、转账 token、或双方认可的其他对价。
- 账面挂账不得对应已过期的储备:对账时按账期切断,防止"储备过期、账面仍挂"的隐性坏账。

### 3.3 角色与准入

| 角色 | 能力 | 准入 |
| --- | --- | --- |
| 使用方(B) | 发 OpenAI 格式请求,验收据,查自己流水 | 在出借方 allowlist 内 |
| 出借方(A) | 声明闲量,代理转发上游,签收据,记流水 | 自主声明;承担封号风险 |
| 引导节点 | rendezvous 注册/查询 | 底座已有,无特权 |

任一节点可同时是 A 与 B(余额/闲量是流动的,非固定角色)。

## 4. 核心流程:预授权-结算两阶段

```
B                        A                        上游
| 1. 请求(OpenAI 格式)    |                        |
|  req_id, 模型, max_tokens|                        |
|------------------------>| 2. 校验:allowlist/模型白名单/余额净差上限
|                         | 3. 冻结:est = f(输入估算, max_tokens)
|                         | 4. 注入自有 key,转发 ---------->|
|                         |<---------- 5. SSE 流式响应 + usage|
|<-- 6. SSE 逐帧转发 ------|                        |
|                         | 7. 结算:解冻 est,按 usage 入账(双边流水)
|<-- 8. 签名收据 ----------|                        |
| 9. 验签,ACK / 争议      |                        |
```

关键规则:

- **幂等**:`req_id`(B 生成的 UUID)在 A 侧去重,重试不产生第二笔记账。
- **断流计费**:上游已返回 usage 则按实际;未返回(A 侧故障/超时)按流式估算入账,
  收据标 `estimated: true`,B 可在争议窗口内申诉。
- **错误透传**:上游 429/5xx/内容拦截映射回 OpenAI 错误格式;A 侧拒绝(冻结不足/非白名单)
  返回结构化错误码,均不产生流水。
- **背压与保活**:流式转发走底座 chunked transfer(1 MiB 帧,FRAME CHUNK/END);
  长生成(分钟级)依赖底座 ping 保活,防 NAT 表过期与 QUIC 空闲超时。

## 5. 协议设计

协议 ID 命名遵循 wire-protocol §3(`/命名空间/名字/版本`,版本纯数字),业务协议与内置协议同机制、无特权:

| 协议 ID | 职责 | 消息编码 |
| --- | --- | --- |
| `/llm-share/offer/1` | 能力声明:模型清单/可出借余量/账期/溢价系数(预留)/TTL;经 rendezvous 签名注册,亦可 mDNS 局域网广播 | JSON |
| `/llm-share/proxy/1` | 代理流:请求帧(JSON, OpenAI 格式 + req_id) -> 上游 -> SSE 逐帧转发;错误帧结构化 | JSON + chunked |
| `/llm-share/ledger/1` | 收据推送/验签 ACK/争议/账期对账查询 | JSON + Ed25519 签名 |

### 5.1 收据结构(记账的唯一凭据)

```json
{
  "v": 1,
  "req_id": "uuid",
  "period": "2026-09",
  "lender": "PeerId(A)",  "borrower": "PeerId(B)",
  "model": "gpt-4o",
  "usage": { "input": 1234, "output": 5678 },
  "estimated": false,
  "upstream_hint": "openai",
  "ts": 1725400000,
  "sig": "Ed25519(A, 上述全字段规范化序列化)"
}
```

- B 验签后 ACK;超争议窗口(默认 24h)未争议即终局入账。
- 争议提交双方流水对质;Phase 0 无第三方仲裁,靠白名单准入(信不过就别开)。
- 流水 append-only,余额是视图;双方各持全量本地副本,对账协议比对哈希链。

### 5.2 能力声明字段

```json
{
  "peer": "PeerId(A)",
  "models": ["gpt-4o", "deepseek-v3"],
  "spare": { "gpt-4o": 1500000, "deepseek-v3": 999999999 },
  "period_ends": "2026-09-30",
  "max_per_req": { "gpt-4o": 128000 },
  "rate_limit": { "rpm": 10, "concurrency": 2 },
  "ttl": 3600
}
```

`spare` 是声明的闲量(软约束,以预授权实际校验为准);进阶可由历史消耗曲线预估,动态下调。

## 6. 组件与底座映射

| 新组件 | 职责 | 依赖底座 | 行数预算 |
| --- | --- | --- | --- |
| `crates/llm-share-ledger` | 流水账本/冻结/净差/收据验签/对账 | 无(纯应用层,Ed25519 复用 p2p-identity) | ~600 |
| `crates/llm-share-proxy` | OpenAI 协议桥接/上游 HTTP 客户端/SSE 转发 | p2p-protocol(request-response + chunked) | ~600 |
| `crates/llm-share-offer` | 能力声明组装/订阅/选路 | p2p-discovery(rendezvous/mDNS) | ~300 |
| `apps/cli` 或 GUI 扩展 | 配置(allowlist/key)、流水查询 | p2p facade | 按宿主 |

原则:全部为底座之上的 ProtocolHandler 注册,不改 crates/p2p-* 内核;上游 key 仅存在于出借方进程内存,
可落盘但必须 0600(对齐 p2p-identity 种子标准)。

## 7. 关键机制

### 7.1 出借方自保护(网络的生死线)

- 四件套限额:单请求 `max_tokens` 上限、RPM、并发、账期净差上限(B 累计欠额封顶,超出即拒)。
- 预授权冻结是硬闸:冻结不足直接拒,杜绝超长 context 轰炸烧穿闲量。
- 内容策略:A 侧保留可感知与处置能力(举报入口、按 PeerId 断供、日志留痕)——对应 legal §3.3/§3.5,
  技术中立不免责。

### 7.2 封号责任分摊(出借动机的保障)

- 归因:上游封停 A 账号时,审计 A 侧流水定位涉事 `req_id` 与 B。
- 赔偿:认定 B 滥用(违反协议/明显违法用途)所致,B 以账期内净差为上限抵赔(A 剩余套餐价值超出部分
  属 A 自担的出借风险,白名单准入即接受该风险)。
- 处置:B 进 A 的黑名单并可广播至互助圈(A 们共享黑名单,仍属白名单联盟,非全局 PKI)。

### 7.3 隐私边界(双向,如实告知)

- B 的 prompt 以明文经 A 转发(代理模型下 E2E 加密不可能);传输加密由底座 QUIC/Noise 保证。
- A 默认不落盘 prompt,仅留元数据(双方 PeerId/模型/usage/时间);合规要求日志 6 个月,
  留元数据满足 legal §3.2,内容不存。
- B 按此自行选择投递敏感任务与否;A 的声明中应含`retention: none`之类的自述字段,供 B 选路参考。

### 7.4 声誉(Phase 1)

- 本地统计:成功率、延迟分位、收据争议率、封号牵连记录。
- 进能力声明作为选路因子;不做全网声誉链(过早去中心化治理是自找攻击面)。

## 8. 合规边界(硬约束,全文对齐 p2p-legal-risk-cn.md)

本方案 barter 记账(不可提现、不可转让、无独立代币、月底清账)不构成虚拟货币发行;
以下为红线,任何阶段不得触碰:

- R1 不做充值/变现/交易通道(legal §3.8:"积分/激励体系严禁可交易、可兑现的代币化设计")。
  若未来引入积分,必须单向、仅抵扣、不可转让不可兑现,且过法务重审。
- R2 不做资金归集/借贷撮合/增信(legal §2 金融 P2P 禁区)。
- R3 不做翻墙/国际信道规避;出借方代理的上游 API 访问本身由出借方以自身合规方式完成(legal §3.7)。
- R4 内容责任:具备感知/处置/留痕能力,违法用途协议明禁、发现即断供(legal §3.3/§3.5)。
- R5 日志:元数据留 6 个月;实名制/等保/App 备案在公开运营时触发,白名单小圈子阶段不触发(legal §3.1)。
- R6 上游 ToS:多数提供商禁止共享访问。定位是"朋友间闲量互助、成本共担",不是转售;
  不加价牟利、不公开经营是风险边界,越界即质变(该风险无法代码消除,准入即告知)。

## 9. 分阶段路线图

| 阶段 | 形态 | 交付 | 合规状态 |
| --- | --- | --- | --- |
| Phase 0 | 朋友/白名单 barter 记账网 | G1-G6 全部目标;不含声誉/定价 | 安全侧:互助成本共担,无资金无代币 |
| Phase 1 | 社群池 + 定价 | 风险补偿定价(溢价系数)、净差跨期结算规则、声誉分 | 需复核:定价上线前过一遍 §8 |
| Phase 2 | 开放网络 + 激励层 | 走 Storj/Filecoin 同款演化路径,届时再议 token 化 | 红线区:R1-R5 全量过法务,默认不做 |

Phase 2 只有在 Phase 0/1 出现真实经济需求(持续单向逆差、定价摩擦)后才启动论证;预置即违规。

## 10. MVP 验收口径(Phase 0,可测)

- A1:两个节点经底座互联,B 以标准 OpenAI SDK 指向 A 的代理端点,流式问答成功,响应与直连上游语义一致。
- A2:预授权生效——B 冻结不足(净差超限)时请求被结构化拒绝,上游零调用。
- A3:一笔完整调用后,双方账本各产生一行一致流水,B 持有效收据,验签通过;篡改 usage 后验签必失败。
- A4:`req_id` 重放仅产生一笔流水。
- A5:非 allowlist PeerId 请求被拒;能力声明 TTL 过期后不再被选路。
- A6:断流场景产生 `estimated: true` 收据,争议接口可用。
- A7:`cargo test --workspace` 全绿(账本/收据/幂等/限额单测 + p2p-itest 双节点用例),clippy 零告警。

## 11. 开放问题(待审核裁决)

- Q1 账期口径:自然月还是对齐各家套餐周期(不同出借方周期不同,账期是否按对本地化)?
- Q2 净差上限默认值:按出借方闲量比例还是固定额度?
- Q3 收据争议窗口 24h 是否合适(上游 usage 出账本身可能延迟)。
- Q4 proxy 端点形态:复用 p2p 流(现状设计)还是 A 本地起 localhost HTTP(OpenAI SDK 兼容更顺)?
  倾向后者:SDK 零改造指 SDK -> localhost -> p2p 流 -> A,首版可只做 p2p 流,GUI 版再加 localhost 桥。
- Q5 组件归属:独立新 crate(facade 之外)还是挂 apps/?建议独立 crate,apps 只做装配。
