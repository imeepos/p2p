# 社交化发现（好友模式）方案 v0

状态：草案（2026-09-04）。上游依据：rendezvous 现状见 crates/p2p-discovery；
本轮已落地的削峰改造见「阶段 P0」。

## 1. 问题

rendezvous 当前是"全网大教室"：客户端周期拉取整个 namespace 快照，
邻居表是会话内只增不减的地址簿。两条规模上限：

- 服务端：`MAX_PEERS_PER_NAMESPACE = 512`（M1 护栏）+ 每查询 O(N) 克隆编码；
- 客户端：发现事件与邻居表条目随池规模线性膨胀，N 大后不可用。

结论：全量发现模型天花板 512。更大规模必须换发现语义，而非继续调参。

## 2. 社区实践调研（2026-09-04）

| 系统/规范 | 机制 | 可借鉴点 |
|---|---|---|
| libp2p rendezvous spec r2 | Discover 带 **cookie**（增量游标）与 **limit**（分页），Register/Discover 应答都回 cookie | 渐进同步的规范做法；我们 Query 消息未留 cookie 字段（只增不改可加 tag） |
| 微信/QQ（公开机制） | 好友列表是服务端一行记录，登录拉列表后增量同步；找人按 ID O(1) 索引；在线状态只推给好友（O(K)） | 社交图谱把发现面从 O(N) 收敛为 O(K)，是十亿级规模的根因 |
| BitTorrent tracker | announce 应答返回**随机子集**，不承诺全量 | "发现一些可用邻居"即可满足多数场景 |
| Tox/Kad（调研文档 §DHT） | DHT 122s 无响应除名 | 规模上限的正确答案是分布式发现，中心化 rendezvous 退化为引导 |

共同结论：**按需精确寻址 + 增量同步 + 子集采样**，取代周期全量广播。

## 3. 目标语义：查号台，而非花名册

好友模式下 rendezvous 语义从"每 5s 读全班花名册"变为"查电话簿打电话"：

- 发现 = 对已知 PeerId 的**精确查询**（`Query { namespace, peer_id }`，服务端
  O(1) 应答，现已支持只是客户端未用）；
- 在线状态 = P2P 连接本身 + 探活判离线（PeerDown/PeerLiveness 已有），
  **不需要**服务端在线注册表，也不轮询；
- rendezvous 查询只发生在"需要建连且无 last-known-good 地址"时。

规模算术：10 万节点 × 每节点每小时建连 10 次 = 每小时 10 万次 O(1) 查询
≈ 28 QPS；对比全量模型同规模 ≈ 400 GB/s 出口（差六个数量级）。

## 4. 分层裁决（README 定位："消息语义、存储、业务鉴权不在底座内"）

好友图谱是**业务语义**，放业务层；底座只提供原语：

| 原语 | 状态 |
|---|---|
| 按 PeerId 精确查询（rendezvous Query peer_id 分支） | 已有 |
| 签名注册（Ed25519，pubkey↔PeerId 绑定，防重放） | 已有 |
| 手动登记地址（AddressBook Manual 来源） | 已有 |
| 探活判离线（PeerDown/PeerLiveness） | 已有 |
| 好友请求转发（服务端按 peer 捎信给可能离线目标） | 复用 relay 打洞信令转发模式（control.rs，目标不在线显式拒绝） |
| 好友地址簿持久化 | 缺，P1 补（复用 p2p-identity 种子落盘纪律：0600、tmp+rename） |

## 5. 分阶段计划

### P0 全量模型削峰（已完成，本轮）

- 客户端查询退避：快启动 2×5s 后进入稳态 30s±20% 抖动（cd0793d）；
- 服务端全量应答快照缓存：register 即失效、按条目真实 TTL 重建（8878e36）。

### P1 按需精确查询 + 好友地址簿（可独立交付）

- `RendezvousClient::query_peer(peer_id)`：单查并刷新 last-known-good 缓存；
- 好友表持久化：data-dir 下 `friends.json`（peer_id + 备注 + last-known-good
  地址 + 添加时刻），启动时加载入 AddressBook（Manual 来源，语义不变）；
- 建连路径改造：connect(peer) 无池内连接且地址簿过期时先 query_peer 再拨；
- 验收：断网重启后好友可直拨；发现面不再产生全量查询流量。

### P2 添加好友流程（含鸡生蛋解法）

- 两个从未谋面的节点互相寻得：线下交换（二维码/口令编码
  `peer_id+bootstrap`）或经 bootstrap 精确查询；
- 加好友请求 = 签名凭证帧（复用 sign_register 同型签名），经 relay
  control 的转发模式送达；对端同意后双方各落一条好友记录；
- 好友凭证含双向 PeerId 绑定，防冒名登记；
- 验收：跨网两节点通过 bootstrap 完成互加并互拨成功（新增 itest）。

### P3 可选演进（按需启动）

- Query 增加cookie/limit 字段（只增不改）：全量场景下的增量分页；
- 服务端快照的 epoch 号 + 客户端变更检测；
- namespace 分片（地域/业务前缀分桶，桶内 ≤512）；
- DHT 接管发现、rendezvous 退化为纯引导层（10 万级规模的终态）。

## 6. 非目标

- 不做服务端在线状态推送（重中心化，违背底座定位）；在线语义 = 连接 + 探活。
- 不在本仓实现好友 UI 与关系管理（业务层/GUI 另行立项）。
- 不承诺发现"全部"节点；发现目标收敛为"找到要找的人"。

## 7. 风险

- **冷启动发现**：无好友且无手动地址时新节点没有发现面——保留 mDNS +
  bootstrap 全量查询作为兜底，仅好友模式下关闭全量轮询。
- **地址漂移**：NAT 重映射后 last-known-good 失效——建连失败即回源
  query_peer 刷新（P1 落地），缓存只作加速不作权威。
- **512 上限与新模型共存期**：公共池继续被全量客户端使用，上限维持不动；
  好友客户端迁移后池压力自然下降。
