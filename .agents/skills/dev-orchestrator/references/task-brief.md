# 任务书与派发提示词模板

目录：
1. 完整任务书模板（实现类任务默认用这张）
2. 轻量任务书（预计 5 次工具调用以内的小任务）
3. 好坏对比
4. 实现会话派发提示词
5. 评审会话派发提示词

## 1. 完整任务书模板

按需裁剪字段，但目标 / 验收标准 / 边界 / 产出物四项不可省：

**按任务类型追加差异要求**（frontend / code-quality / architecture / quality-gates）：先看 `SKILL.md`「任务分类与类型规范」的路由表，再查对应 `references/task-spec-*.md`，把该类型的必带约束写进"验收标准/边界"，把验收门并进汇报要求。

```markdown
# 任务 <task-id>：<任务名>

## 目标
一句话说清要产出什么、达成什么可观察的结果。

## 背景（指针，不是内容）
- 本任务在计划中的位置：为什么存在，完成后谁接手
- 必读输入（路径 + 一句话摘要，禁止粘贴大段内容）：
  - `TODO.md` —— 验收口径的唯一来源
  - `AGENTS.md` —— 硬性工作规范（测试优先 / 行数红线 / worktree 协议）
  - `src/<相关模块>` —— 现状：已有 <什么>，缺口是 <什么>

## 验收标准（全部满足才可报 DONE）
- [ ] <可机械核验的条件 1，如：`go test ./...` 全绿，退出码 0>
- [ ] <条件 2，如：新文件先有失败测试再实现，红绿双向>
- [ ] 产出物存在于 `<精确路径>`，格式：<格式/签名/示例>

## 边界（明确不做）
- 不修改 <范围外模块/文件>
- 不引入新依赖；不做 <相邻任务的内容>

## 接口契约
- Consumes：<依赖的产物，精确到名字/类型/路径>
- Produces：<后续任务将依赖的产物，精确到名字/类型/路径>

## 预算与停止条件
- 预算：约 <N> 轮修复 / 工作量上限 <粗粒度描述>
- 立即停止并报 BLOCKED：<条件，如"迁移编号与 main 撞号无法让位">
- 立即停止并报 NEEDS_CONTEXT：<条件，如"接口契约不足以决定实现方向">

## 工作区与汇报
- 在 worktree `<分支名>` 上工作，遵循 AGENTS.md worktree 协议；禁止直接改主干
- 汇报经 `session_link_send_parent` 回报派发你的主会话
- 派发者显式 id：`<主会话 sessionId>`（`send_parent` 解析结果不对或发送失败时，改用 `session_link_send` 定向投递该 id，不重发试错）
- 汇报状态只用：DONE / DONE_WITH_CONCERNS / BLOCKED / NEEDS_CONTEXT
- DONE 汇报必须附：变更文件清单、每条验收标准的核验证据（命令 + 退出码）、顾虑，以及结构化复盘节（格式见下方第 4 节汇报格式；复盘是主会话的裁定输入，不是验收结论）
```

## 2. 轻量任务书

```markdown
# 任务 <task-id>：<一句话目标>
- 读：`<输入路径>`（<一句话说明>）
- 做：<动作>
- 产出：`<路径>`，<格式>
- 停止条件：遇 <条件> 即报 BLOCKED，不自行扩大范围
```

## 3. 好坏对比

| 坏写法 | 问题 | 改法 |
| --- | --- | --- |
| "修复测试失败" | 不知道哪些测试、什么根因 | "修复 `<测试文件>` 中 <N> 个用例：先判断是时序问题还是实现 bug；禁止靠加大超时糊弄" |
| "调研一下方案" | 不知道"够用"长什么样 | 给出对比维度、结论格式、页数上限："输出 ≤30 行对照表，含 <维度1/2/3>，末尾给推荐与理由" |
| 无约束 | 子会话顺手重构一切 | "只改 `<范围>` 内文件；不动生产代码其他部分" |
| "参考任务 3 的做法" | 执行者看不到任务 3 | 把需要的接口签名 / 约束逐字写进本任务书 |
| 粘贴 200 行源码进任务书 | 浪费 token 且版本易过期 | 给路径 + 一句话摘要，让子会话自己读 |

## 4. 实现会话派发提示词

派发时在任务书外再包一层提示词（作为 `session_link_create` 的 greeting 下发）：

```text
你是本项目的实现会话，负责完成任务书 <task-id>。

第一步先读：任务书全文 + AGENTS.md + 任务书列出的输入路径。

对需求、验收标准、接口契约有疑问，开工前一次问清（报 NEEDS_CONTEXT）；
不要带着猜测开工，也不要中途擅自假设。

执行要求：
1. 严格按任务书的验收标准与边界工作，范围外的问题记录在汇报里，不顺手修
2. 测试优先：先写失败测试（红），再实现转绿；修复类任务先写复现测试
3. 提交纪律按 AGENTS.md：只 add 显式路径，message 写清改动与原因
4. 自验只做轻量门禁（lint + 聚焦测试）；不要跑全量重型验证，那是主会话的活
5. 禁止派发任何子会话；禁止合并进主干；禁止改动其他会话的 worktree

汇报通道：
用 session_link_send_parent 把汇报回报给派发你的主会话（自动解析上级，无需查 id）；
解析出的上级不对或回报发送失败时，改用 session_link_send 定向投递任务书里的派发者显式 id，不重发试错；
禁止 session_link_list 枚举兄弟会话打听，禁止与其他子会话直接互通。

汇报格式：
STATUS: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
变更：<文件清单 + 一句话each>
验收对照：<逐条列验收标准 → 证据（命令/退出码/输出摘要）>
顾虑与移交事项：<给主会话和下一个任务的注意事项>
复盘（终态汇报必附，≤10 行；修复轮只写"本轮增量"）：
- 完成度：<做完 vs 计划；砍了什么、为什么——克制不是简陋，砍范围不砍质量>
- 新事实：<执行中发现的环境/领域事实+证据指针；无则"无">
- 缺陷与隐患：<过程中暴露的问题，含位置>
- 过度设计候选：<哪里可能做重了+理由；只提候选不定论，主会话裁决>
- 下游影响：<Produces 与契约相符性；对 Consumes 邻居的影响>
- 预估偏差：<预算 N 实际 M；原因一句话>
- 遗留处置：<未做事项→建议去向：TODO.md / Known Issues / 新任务书 / 丢弃>
- 下一步建议：<按优先级，≤3 条>
- 大白话总结：<一句话>
```

## 5. 评审会话派发提示词

```text
你是只读评审会话。评审 <范围/分支> 相对 <基准 commit> 的变更，
不得改动工作区、暂存区、HEAD 与分支状态；需要对照其他版本时自查历史。

输入：任务书（验收标准）+ 变更范围（`git diff <base>..<head>` 自行查看）。

检查项：
- 验收符合：逐条对照任务书验收标准，缺一即报
- 测试质量：测的是真实行为还是 mock 假象；回归测试是否做过红绿双向
- 边界纪律：是否越界改动；接口契约（Produces/Consumes）是否与任务书一致
- 常规质量：错误处理、行数红线、命名、依赖

输出格式：
Strengths: <具体优点，先说>
Critical（必须修）: <缺陷/安全/数据丢失/验收未达>
Important（合并前应修）: <架构问题/测试缺口/错误处理缺失>
Minor（记录即可）: <风格/小优化>
结论: 通过 | 修复后通过 | 不通过
严重度自己校准，不要把一切标成 Critical；对计划本身的质疑单独列出。
```
