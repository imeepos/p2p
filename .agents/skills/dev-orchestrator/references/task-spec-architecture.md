# 任务类型规范：架构设计（architecture）

目录：1. 何时打此标签 → 2. 任务书差异 → 3. 验收门 → 4. 高频坑 → 5. 深入阅读

## 1. 何时打此标签

技术方案/spec/目录骨架/分层与依赖/ADR 决策记录/上下文工程（memory bank、代码库地图）类任务。产出物是"约束后续编码的决策与结构"，不是可运行代码。

## 2. 任务书差异（在通用模板上追加）

**产出必须可判定**——方案/spec 不是给人看的说明文，是给执行会话的契约：

- 每条要求带输入输出、失败态、验收命令；"尽量高可用"不合法，"p99 ≤ 500ms、失败重试 2 次"才合法
- 写不出验收命令的要求，退回计划阶段重写（与"计划里禁止占位符"同罪）

**规模匹配**——先声明任务量级再选流程：

- 小修小补：直接走普通任务书，禁止强上全套 spec 流程（为一个 bug 生成 16 条验收标准是负收益）
- 中型 feature：plan 先行（研究 → 提案 → 你确认 → 再实现），任务书写"先报方案再动工"
- 新骨架/新模块：先"立宪"——把不可变原则、分层方向、命名约定落成决策文件，后续所有任务书引用它

**上下文预算**（防检索污染与注意力稀释）：

- 注入代码 ≤4000 行，超出只给接口定义/摘要
- 过期或废弃代码必须打"REFERENCE ONLY, 禁止沿用其结构"标记
- 中小库用指针 + 让子会话按需检索；不要为小任务预建全库索引

**决策记录衔接**：方案类任务产出 ADR 草稿时，必读输入必须含既有决策目录（如 `docs/notes/adopted/`），草稿须给 2–3 个备选与舍弃理由；你修订后当天过账（项目决策制度）。

## 3. 验收门（主会话机械核验）

- [ ] 决策/spec 文件落盘在约定路径，含 why + 放弃了什么（备选方案）
- [ ] 每条要求可判定：能指出"用什么命令/检查核验它"
- [ ] 分层/依赖方向变更已通过适应度检查（已有检查器时贴运行输出；未建时在汇报里列"建议纳入门禁的方向规则"）
- [ ] 与既有决策无冲突；有推翻时按项目制度加 Amended 注记而非改原文
- [ ] 下游任务书可以直接引用该产出（Produces 精确到路径与结构）

## 4. 高频坑与对策

| 坑 | 对策 |
| --- | --- |
| 模型越强产出越臃肿（Volume-Quality Inverse Law） | 把代码体积/耦合度写进验收指标，不只测功能 |
| "虚假的控制感"：评审一堆 markdown 却没约束实现 | spec 必须落到可执行验收命令；方案任务以"下游任务书可引用"为完成态 |
| AI 倾向新写代码块而非复用（克隆 4 倍激增） | 任务书加"生成前先搜索可复用模块，复用优先于新建"；克隆率纳入后续门禁候选 |
| 检索片段混入废弃代码带偏实现 | 过期代码打 REFERENCE ONLY 标签 + 行数硬上限 |
| 约束越加越多，agent 通过率掉 30 分 | 门禁规则少而硬：只保留真正不可让步的方向性规则 |
