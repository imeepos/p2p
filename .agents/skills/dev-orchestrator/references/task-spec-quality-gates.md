# 任务类型规范：质量门禁（quality-gates）

目录：1. 何时打此标签 → 2. 任务书差异 → 3. 验收门 → 4. 高频坑 → 5. 深入阅读

## 1. 何时打此标签

CI 流水线 / required checks / pre-commit 与 hooks / 防假绿机制 / AI 评审接入 CI / 度量采集类任务。产出物是"机器执行的关卡"，验证方式是"在主干实跑并核对真实退出码"。

## 2. 任务书差异（在通用模板上追加）

**阈值逐字写明**——门禁任务的验收标准必须给数值与命令，不给数值的门禁是摆设：

- 门禁四件套（lint + typecheck + test + build）进 required checks；每项给出确切命令与预期退出码
- 本地 pre-commit 只放 <10 秒、≤5 项、只查变更文件的检查；重的全进 CI——**本地是便利，CI 才是门禁**（--no-verify 只能绕过本地）
- 新增阈值先问"误报率谁兜"：宁少而硬，规则累积本身会让执行者通过率下降、团队绕过门禁

**hooks 类任务附语义表**（最高频配置错误源）：

- 退出码：0 放行 / **2 拦截** / 1 仅算"执行出错"不拦截
- HTTP hook：4xx/5xx 不拦截只记录；要拦截必须 2xx + `permissionDecision: deny`
- 防死循环：Stop hook 内禁止写文件；PostToolUse 禁止改文件；连续 block 设上限（官方 ≈8 次）
- 配置进仓库（如 `.claude/settings.json`），团队共享同一套门禁

**防绕过**（AI 时代新增的假绿源头）：

- AI 会话产生的提交必须同样触发 CI（默认 bot token 的 commit 不触发 CI = 裸奔进主干）
- 门禁结果必须来自指定来源（指定 App/指定 job），防止旁路检查替代
- 收尾核验禁链式命令：`cmd > log 2>&1; echo EXIT=$?` 逐项核对，管道不吃退出码

## 3. 验收门（主会话机械核验）

- [ ] 在主干实跑完整门禁，逐项贴出真实退出码（不用管道 $?）
- [ ] 故意制造一次失败（改坏一行/临时断言），确认门禁真的红——门禁没有红过的证据等于没建
- [ ] 绕过路径实测：`--no-verify` 只能绕本地、required check 不可被旁路提交绕过
- [ ] hooks：拦截路径（exit 2）与放行路径（exit 0）各实测一次；确认无死循环风险
- [ ] 度量类产出：采集口径写明（"只认最终入库代码"类），防虚荣指标

## 4. 高频坑与对策

| 坑 | 对策 |
| --- | --- |
| 管道吃退出码（`cmd | tail` 的 $? 是 tail 的） | 逐项 `cmd > log 2>&1; echo EXIT=$?`；项目红线已有，任务书重申 |
| 拿 healthz/构建绿/截图存在当行为证据 | 门禁验收只认业务级失败注入实验 |
| 误报率高 → 团队亲手关掉门禁 | nit 上限、白名单、验证 bar（file:line 证据）随门禁一起交付 |
| 成本失控（AI 评审按 push 翻倍） | 评审触发按"PR 创建一次"；轮数/超时/并发/月度上限配齐 |
| AI 口头宣布"测试全过" | 收尾核验收证据链：测试输出 + 退出码，不接受转述 |
