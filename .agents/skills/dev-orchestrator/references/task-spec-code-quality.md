# 任务类型规范：代码质量（code-quality）

目录：1. 何时打此标签 → 2. 任务书差异 → 3. 验收门 → 4. 高频坑 → 5. 深入阅读

## 1. 何时打此标签

三种子类，任务书里必须注明是哪一种：**评审调优**（接入/调教 AI 评审、降噪）、**测试补齐**（为新旧代码补测试）、**规则治理**（AGENTS.md/CLAUDE.md/评审规则文件的增删改）。

## 2. 任务书差异（在通用模板上追加）

**评审调优类**——任务书必带"评审哲学"（这是降噪实证里唯一同时降低噪音与保住召回的注入物）：

- 只在置信度 >80% 时发言；一条评论一句话；只提可行动项，不做观察式点评
- 优先领域白名单逐字列出（如：硬编码密钥、竞态、错误吞噬、违反既有模式）
- 噪音上限：nit 类发现 ≤5 条，其余摘要报数；行为类断言必须带 `file:line` 证据，否则不报
- 北极星指标：address rate（作者合并前真正处理的评论比例）；被驳回的发现记入负样本清单反哺规则

**测试补齐类**——验收清单逐条进任务书：

- 每个测试 ≥1 个业务语义断言；失败路径至少测一条；禁恒真断言
- 只 mock 外部 IO（HTTP/DB/文件）；核心业务逻辑不许整体 mock；用 spy 验证副作用真的发生
- 时间/随机必须可注入；遵循项目红线：测试替身必须真实执行状态流转、mock 默认值与真实现同源
- 红绿双向：修复类先在未修复代码上跑红，再转绿；红绿证据链进汇报

**规则治理类**——三桶法，产出物是"迁移表"：

- 确定性规则（禁改迁移、提交纪律、门禁四件套）→ 迁去 hooks/CI 机械强制
- 判断性规则（匹配既有风格、拆分时机）→ 留在文档
- 空话（"写好代码"类）→ 删除
- 目标 50–200 行高密度文件；变更附行数对比与迁移去向表

## 3. 验收门（主会话机械核验）

- [ ] 评审类：每条发现都有 `file:line`；nit 不超上限；无"maybe/consider"式猜测评论
- [ ] 测试类：先红后绿的证据链（命令 + 输出摘要）；抽查 2–3 个测试确认断言语义而非 mock 假象
- [ ] 规则类：迁移表存在且与实际文件一致；文档行数在预算内；确定性规则确有对应 hook/CI 配置
- [ ] 实现与评审是不同会话（maker/checker 分离）；评审会话只读

## 4. 高频坑与对策

| 坑 | 对策 |
| --- | --- |
| 裸 LLM 评审不可用（79% 是没人 care 的 nit） | 先注入规则上下文 + 负样本过滤，再谈接入 |
| 只调 prompt 不建反馈回路，噪音随时间回潮 | 负样本清单/拦截规则落成文件，随任务书版本演进 |
| 覆盖率好看但测试无效 | 覆盖率只做参考不做门禁；语义断言清单才是验收 |
| 评审上下文堆全库反而更差（注意力稀释） | 评审会话只喂结构化 diff + 摘要 + 优先领域白名单 |
| 同模型自审盲区 | 评审会话与实现会话用不同模型（至少不同会话实例） |
