# 消息积压：静默排队、陈旧批量倾泻与排水协议

子会话的回报不是即时到达的——它们在一只看不见的队列里等你。本文件是**主控侧**的应对协议。目录：
1. 机制事实（为什么会积压、为什么你看不见）
2. 事故形态：陈旧批量倾泻（真实代价）
3. 排水协议：一批到达时的四步处置
4. 陈旧性判定：三条机械检查
5. 预防：让积压变浅、让报告自带时效标
6. 红线

## 1. 机制事实（别赌，这是已实证的宿主行为）

- session-link 投递给 running 会话只有一种模式：**入队，回合边界才被吸收**。修正/汇报延迟 = 目标当前回合的剩余时长，没有"工具间隙注入"的抢占通道。
- 插件会在投递前尝试打断忙碌目标（`interruptTargets` 默认开），但**目标是你自己时打断无意义**——你正在跑的回合不能被这条消息插断，回报只能在队列里等你回合结束。
- **队列深度不可见**：`session_link_list` 只给出 `blank` / `running`，不暴露积压条数。你无法从任何工具面看出"还有 3 条回报在等"。`talk`/`collect` 的 `pending` 只覆盖该次 talk 的回复，不覆盖通用收件箱。
- 因此：**你跑一个长回合（跑全量门禁、长时间验收）= 这段时间内的全部回报原地堆积**，回合结束时一次性到达。

推论：回合长度直接决定积压深度。你越"专心干活"，越容易制造一次倾泻。

## 2. 事故形态：陈旧批量倾泻（真实代价）

一次倾泻 = N 条**按发生顺序排队、但按到达顺序一起交付**的消息。典型特征：

- 同一子会话的**多封重发/交叉信**同时到达（它以为投递失败，反复重发，全部积压）。
- 报告描述的**形态早已被取代**：它报 tip=X，而 X 后来又 rebase 了三轮，你实际合并的是 Y。
- **过时结论混在新鲜结论里**，外观完全一样——都长得像"刚发生的汇报"。

真实代价（2026-09-15 向量波实录）：
- 一封 22:36 的回报直到次日 01:02 才到，期间子会话三次重发全部积压，主控一份都没收到——**主控以为子会话没回报，子会话以为投递失败**，双方在信息真空中各自推断。
- 倾泻的旧报告描述的 tip 已被合并；若照其字面执行，会去"验收"一个早已进主干的形态，或对已合并工作重复下指令。
- 用户手动 flush 是常见触发点：积压可以横跨整个波次，收官后才一次到达。

**关键判别**：一批消息同时到达 ≠ 一批事件同时发生。到达时间是你的回合边界，不是它们的事发时间。

## 3. 排水协议：一批到达时的四步处置

积压到达时**不要逐条当新消息处理**——按批处理：

1. **先归组，不先行动**：按子会话/任务分组，同一任务的 N 封按时间排序。多封重发往往内容等价，取**最晚一封**为准，其余只作历史。
2. **以盘上证据校准，不以消息字面为准**：对每一组问「它描述的形态现在还在吗」——跑 §4 的三条检查。已进主干的报告 = 历史记录，不是待办。
3. **只对"未被盘上证据覆盖"的项行动**：仍悬空的裁定请求、仍存在的冲突点、仍未闭合的 CONCERNS。已被你后续验证覆盖的"提醒"（例如它请你复验某窗口，而你此后已多轮亲跑全绿）直接归档，不重复劳动。
4. **一次性回执**：若对方仍在（未归档），用**一封**合并回执覆盖全组，不要逐封回。若已归档，改写进账本留痕——不回执但必须留证。

> 判定"重复劳动"的口径：盘上证据（git log / 主干门禁 / 产物文件）**强于**消息里的请求。子会话无法知道它汇报之后主干发生了什么，它的"建议复验"可能在你收到时早已被你亲手验过。

## 4. 陈旧性判定：三条机械检查

对每封延迟到达的回报，跑这三条（成本极低，能拦掉绝大多数误动作）：

1. **该形态是否已在主干**：`git merge-base --is-ancestor <它报的 tip> main`。退出码 0 = 已合并 = 报告是历史。非 0 也可能是 rebase 重写了历史——用内容等价核验兜底（见下）。
2. **它报的分支/worktree 是否还在**：`git branch --list <分支>`、`git worktree list`。已被你清理 = 该任务已收口，报告只作留档。
3. **它请求的动作是否已被你做过**：对照你发出的账本行与主干提交时间。请求"复验窗口 X"，而你此后已跑过完整门禁 → 已覆盖。

> rebase 会重写 tip，使检查 1 对旧 tip 返回非 0（对象仍在，只是不在线上）。此时改用内容等价：`git log --all --grep` / 直接 `git show <旧 tip>:<文件>` 与主干对比，确认其沉淀（如 memory 条目）确已在主干。

## 5. 预防：让积压变浅、让报告自带时效标

**主控侧（你能做的）**：

- **缩短回合**：长耗时验证（全量门禁、e2e）前后各留一次消息检查点，别让一个回合横跨半小时。门禁跑在后台 job 里、回合内做别的编排工作，是兼顾吞吐与响应性的正解。
- **重要结论要回执，不要单向**：需要立即答案的用 `talk`（有界等待）而不是等 `send_parent`。`talk` 超时也留 `claimToken`，可用 `collect` 补收——这比"等它主动汇报"多一层确定性。
- **归档前必收**：归档是最后一步且不可逆，归档即永久失联。归档前把该会话的汇报收进账本（`session-protocols.md` §6）。
- **盘上账本优先于消息**：把汇报逐条落账本文件。消息会丢、会迟、会乱序；账本文件不会。**投递不可靠时，文件是权威通道。**

**派发侧（写进任务书）**：

- 要求终态汇报采用固定字段，至少含：`状态枚举` / `分支 tip` / `基点` / `门禁退出码` / `diff --stat`。有 tip 与基点，§4 检查 1 就能机械跑——报告自带时效标。
- 要求"若投递存疑，改写进度文件并留权威节"：真实有效的兜底。子会话连续重发只会加深积压，改落盘则主控随时可读。
- 要求 CONCERNS **默认落盘成文件**（进度文件的专节），消息只做指针。消息丢了，文件还在。

> 已知工具面缺口：无"积压条数"查询。落盘约定正是为了绕开它——**别指望能查到队列，要设计成不需要查**。

## 6. 红线

- **禁止把"一批同时到达"当作"一批同时发生"**：处理前必须按 §4 校准，禁止凭到达顺序推断事件顺序。
- **禁止对延迟报告的字面结论执行破坏性动作**（回滚、重派、撤销合并）而不先核盘上现状。
- **禁止把子会话的"建议复验/提醒"当待办照做**：先查该窗口/该形态此后是否已被你自己验证覆盖；已覆盖则归档不回工。
- **禁止假设"没收到回报=子会话没干"**：收不到可能是积压。判定子会话进展一律以产物文件时间戳为主证，不以"它的消息到没到"为准。
- **禁止在未收编汇报前归档会话**：归档即永久失联，倾泻中的报告会连同会话一起变成不可问询的历史。
