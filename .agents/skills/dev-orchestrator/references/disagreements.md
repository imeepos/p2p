## 1. 分歧的来源

| 来源 | 典型表现 | 第一反应 |
| --- | --- | --- |
| 实现 vs 验收标准 | 子会话报 DONE，验收对不上 | 拿证据打回，附具体差距 |
| 评审 vs 实现 | 评审说有问题，实现者说没问题 | 你按证据阶梯裁定，不允许会话间拉扯 |
| 计划 vs 现实 | 计划假设的前提不成立（接口不存在/依赖变了） | 改计划并记账，让计划服从事实 |
| 会话 vs 会话 | 两个子会话改同一处、产出互不兼容、撞号 | 停一个，按阶梯裁定先后与归属 |
| lead vs lead | 同工作区另一主会话与你争同一 scope / 资源 / 流程口径 | 走 `multi-lead-protocol.md` §7：scope 内 owner 裁决，跨 scope 一轮书面交换后升级到人 |

## 2. 裁定流程

**裁定而非搁置**：计划运行期间不为等一个裁决而整体停摆；错误的裁定可返工，停摆的会话只消耗时间。

1. 定位分歧实质：是事实之争（查证据）还是口径之争（查事实源）还是价值之争（你来拍板）。
2. 按下面的证据阶梯找依据，找到即停。
3. 记账本：`Ruling: <裁定> — <依据> — <错了的代价>`。
4. 把裁定与理由同时通知受影响的双方，需要改任务的同步改任务书与账本。

## 3. 证据优先级阶梯

高者胜，逐级往下：

1. **安全与硬性红线**（项目规范中的禁止项）——一票否决，无例外
2. **行为证据**：测试红绿、退出码、日志、diff——注意区分"事实如此"与"应当如此"，实测行为与 spec 冲突说明实现错了，不是 spec 错了
3. **TODO.md / spec**：验收口径的唯一来源
4. **计划文本**：计划是 spec 的论证，与 spec 冲突时改计划
5. **子会话意见**：听完再称重，不因声音大让步
6. **直觉**：只在以上全空时使用，且必须标注为临时裁定

注意：没有"理论上不可能"——先插桩拿证据，禁止把分歧归因为环境怪象。

## 4. 共享资源冲突（撞号类）

迁移号、路由、权限码、中央登记文件这类"worktree 隔离不了"的资源：

- 先查主干与各未合并分支的实际占用，再定编号/命名；以"已进主干者优先，后来者让位"裁决。
- 让位方由你指派修改（通常打回其会话小改一笔），登记文件类改动压成独立小提交。
- 裁决记入账本 Rulings，防止同一冲突反复发生。

## 5. 熔断与升级到人

- **修复熔断**：同一任务第 5 轮仍不过 → 停止循环，你逐条裁定剩余发现：可带病放行的记 Ruling 放行，不可放行的重新拆任务。
- **升级到人**只有四种触发，其余一律自己裁：
  1. 不可逆或破坏性操作（删数据、改生产配置）
  2. 安全敏感动作（密钥、鉴权、外部暴露面）
  3. worktree 之外的副作用：合并主干、推送共享分支、发布
  4. 计划烂到每条路都是猜（不是"有点难"——难是拆任务的理由，不是停工的理由）
- 升级时带三样东西：已尝试的措施与证据、当前的分歧点、你推荐的选项。禁止裸问"怎么办"。

## 6. 决策记录衔接

- 裁定中产生的**不可逆/难逆决策**（选型、库表结构、目录骨架、鉴权方案）：当天写入 `docs/notes/adopted/`，记 why + 放弃了什么。
- 决策被推翻：不改原文，加 `Amended` 指向新记录。
- 裁定中暴露的**新踩坑**（流程性反复犯错）：按项目 self-evolving 流程沉淀到项目记忆目录（路径见项目规范），防止下轮重犯。
- 一次分歧若靠同一条依据反复裁决 ≥2 次，把它固化进 TODO.md 的全局约束或项目规范，让它不再需要裁决。
